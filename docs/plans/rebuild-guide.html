Architecture & build order

Ticket-to-PR Factory

An agent pipeline that takes a well-specified ticket from a board to a reviewed pull request, with a human gate at both ends. Distilled from the working etrm-factory build for a from-scratch rebuild.

What it is

A ticket labelled agent-ready triggers a fully automated run: an analyzer decides the ticket is workable, a planner explores the repo and writes a plan, an adversary attacks the plan, an implementer executes it in an isolated build, a reviewer attacks the diff, and the run ends at a pull request a human must merge. Every stage failure reports back to the ticket; nothing merges or deploys itself. A learning loop turns review findings into lessons that inform future runs.

Security model, in five invariants

  • Agent sessions hold Bedrock-only credentials. A dedicated role that can invoke models and nothing else; the container role's credential source is stripped from the subprocess env.
  • Workspaces are credential-less. Remotes scrubbed after clone; tokens passed via git credential helper or unexported shell vars, never argv or URLs; only deterministic harness steps push, only to agent/* branches. Redact token shapes from every failure path — child-process errors quote the failing command into logs.
  • Ticket text is data, not instructions. Harness code wraps it in delimiters (strip look-alikes first); the analyzer carries an injection tripwire; the reviewer treats security-weakening changes as blocking even when the ticket asks for them. The uncorrelated checks are human: who applies the label, and who merges.
  • Protected paths. When the pipeline can modify its own repo, the files that constrain it (workflows, IAM, buildspec, injection code, target definitions, eval cases) are enforced off-limits mechanically in the build and by the reviewer — and told to the planner so plans never propose them.
  • Humans gate both ends. Restricted label application in; PR review and manual deploys out. Never auto-merge.

Everything else

Learning loop: findings persist to DynamoDB on every review exit (best-effort, never fails a run); the curator writes lessons to semantic memory; planner, implementer, and reviewer retrieve them — the reviewer blind-first, lessons checked only after its own pass. Observability: OTEL via the platform's preload path, EMF metrics per run/stage (tokens, duration, estimated cost), stage-summary log lines as the quick progress view. Delivery: unit tests gate the container build; CI + manual eval-sweep and deploy workflows via OIDC; a graded eval ticket set runs against the deployed runtime before prompt/model/graph changes ship.

Build order

The order that worked. Each step is demonstrable on its own; resist starting the webhook or memory before the core loop earns them.

  1. Prerequisites

    Bedrock model access in your region (regional inference profile IDs, not bare model IDs — and check the account allowlist for the newest models early, it can take a support case). Board + labels (agent-ready, agent-in-progress, agent-blocked). A test target repo with a real test suite and a CLAUDE.md. Secrets in Secrets Manager. Use a GitHub App from day one — per-repo installation tokens, org-owned, nothing long-lived to rotate; a fine-grained PAT works but its repo selection will bite you.

  2. Walking skeleton

    Container that answers /invocations and /ping, deployed to the agent runtime by an idempotent script; invoke it by CLI with an issue ID and echo the issue back. This proves auth, deploy, and logging before any intelligence exists.

  3. Analyzer

    Small fast model with schema-validated structured output; read the ticket, comment its assessment back, gate on suitability. Calibrate it: block on genuinely ambiguous intent, never on details discoverable by reading the repo.

  4. Planner ⇄ adversary

    Headless Claude Code in plan mode over a shallow, credential-less clone; pipe prompts via stdin; resume the session for revisions. Adversary critiques with structured output; loop imperatively with a hard cap. Graph frameworks with AND-dependency semantics deadlock on cyclic edges — run all loops inside nodes.

  5. Implementer in CodeBuild

    Fresh container per build: clone, scrub remote, install, run Claude Code against the approved plan under Bedrock-only creds, then mechanical gates — typecheck, tests, protected paths — before the harness commits, pushes, and opens the PR. Plan in via S3; transcript out to S3.

  6. Reviewer + revision loop

    Fresh-context review of the PR diff against plan and acceptance criteria; findings-only output format with a retry-once guard; post each pass verbatim to the PR (COMMENT only). Blocking findings trigger one revision build; cap-hit or implementer disagreement escalates to the human with everything visible. Wire the label lifecycle and the every-failure-comments rule now.

  7. Webhook trigger

    Lambda with HMAC verification, transition-only firing, and the expiry-aware idempotency claim (ticket systems deliver several events per label change — absorb the burst, release on terminal state). This is the moment the loop closes: label a ticket, get a PR.

  8. Tests, evals, CI

    Unit tests over every pure piece (parsers, predicates, prompt assembly, redaction), gating the image build. A graded eval set — well-specified feature, known bug, ambiguous, vague, injection — run against the deployed runtime with deterministic scoring and cleanup. CI + manual deploy workflows via OIDC.

  9. Learning loop

    Findings table, curator, semantic memory with per-repo namespaces, retrieval into the three consumers. Keep every memory call best-effort. Expect low retrieval scores (~0.4–0.5) for clearly related content — set floors empirically. Metadata fields have small hard limits (e.g. 5-item lists) — truncate in a tested pure mapper.

  10. Multi-repo + self-hosting

    A targets file (slug, workdir, verify commands, protected paths, memory namespace) with routing by label — plus source→target bindings: which board may dispatch to which repos, enforced deterministically at ingress and at target resolution. Only then point it at its own repository.

Do differently this time

  • GitHub App, not PAT — covered above; it also makes PR attribution honest.
  • Source→target bindings from the start, not label-only routing — a mis-labelled ticket once delivered a feature into the wrong repository.
  • Failure detail reaches the ticket. "Run failed" without the failing gate's actual output costs a debugging cycle every time; extract the reason (redacted) into the failure comment from day one.
  • Tell the planner the constraints the build enforces — a plan that violates a mechanical gate burns a full build to find out.
  • Plan model quota headroom. Daily per-model token caps are real and often non-adjustable; five runs in a day hit the Opus ceiling. Spread stages across model tiers and know your reset time.
  • Egress control before real code — private subnets + NAT chokepoint; the open-egress runtime was the accepted gap of the prototype.
Gotchas that each cost a debugging cycle
  • CodeBuild shells are dash, not bash — no pipefail; a YAML scalar containing : becomes a mapping. Quote commands, redirect instead of pipe.
  • Claude Code as root needs its sandbox env flag; prompts go via stdin — argv echoes the whole prompt into error messages.
  • Ticket-system JSON can contain raw control characters — parse leniently.
  • New IAM roles fail downstream validation for ~10–20 s — make setup scripts re-runnable and just re-run.
  • OTEL on a managed runtime: use the platform's exporter path; a vanilla OTLP exporter exports to nowhere, silently. And platform-side span ingestion can break with zero client-side errors — verify spans actually land after every change.
  • The pipeline's own status comments must be filtered out of the analyzer's view, or it reads them as suspicious content.
  • DynamoDB TTL deletion is lazy by hours — never rely on it for logic; compare timestamps.
